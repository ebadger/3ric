# WinAppSDK Migration Guide: Lessons Learned

## Overview

This document captures hard-won knowledge from migrating a C++/WinRT WinUI 3 desktop application from Windows App SDK 1.3 to 1.6. It focuses on false assumptions, non-obvious requirements, and solutions that would have saved significant debugging time if known upfront.

The guidance here is generally applicable to any C++/WinRT WinUI 3 packaged desktop app using NuGet-based SDK integration.

---

## Part 1: Migration Pitfalls and Solutions

### 1. WebView2 Is No Longer Bundled in the SDK Package

**False assumption:** All WinRT types referenced by WinUI 3 controls are included in the WindowsAppSDK NuGet package, just as they were in 1.3.

**Reality:** Starting with WinAppSDK 1.6, `Microsoft.Web.WebView2.Core` types are in a separate NuGet package (`Microsoft.Web.WebView2`). The SDK's WinUI headers (`Microsoft.UI.Xaml.Controls.h`) include `winrt/Microsoft.Web.WebView2.Core.h`, which means CppWinRT must be able to resolve these types even if your app does not directly use WebView2.

**Symptom:** CppWinRT fails during projection generation with errors about unresolved `Microsoft.Web.WebView2.Core.CoreWebView2` types.

**Solution:** Install the `Microsoft.Web.WebView2` NuGet package and ensure its winmd is available to CppWinRT. The winmd lives at `packages\Microsoft.Web.WebView2.{version}\lib\Microsoft.Web.WebView2.Core.winmd`.

---

### 2. CppWinRT Version Mismatch Between NuGet and Windows SDK

**False assumption:** The CppWinRT tool version in the NuGet package and the `winrt/base.h` shipped with the Windows SDK are compatible.

**Reality:** The Windows SDK ships its own `cppwinrt\winrt\base.h` (e.g., version 2.0.250303.5 in SDK 10.0.26100.0), while the `Microsoft.Windows.CppWinRT` NuGet package may ship an older tool (e.g., 2.0.230524.4). Generated projection headers embed a version check via `#pragma detect_mismatch` and `static_assert`. If you include the SDK's cppwinrt path in your include directories, the newer `base.h` conflicts with headers generated by the older tool.

**Symptom:** `static assertion failed: 'Mismatched C++/WinRT headers'` during C++ compilation.

**Solutions (pick one):**
- **Upgrade the CppWinRT NuGet** to match the SDK version (e.g., 2.0.250303.5+).
- **Do not add the SDK's cppwinrt path** to `AdditionalIncludeDirectories`. Instead, ensure the CppWinRT NuGet tool generates its own `base.h` into the Generated Files directory. This happens automatically when CppWinRT processes platform inputs (winmds passed via `-in`).
- **Make WebView2 a platform input, not just a reference.** If WebView2 is passed as `-ref` only, CppWinRT may not generate `base.h` itself. Adding it via `CppWinRTPlatformWinMDReferences` (which feeds into `-in`) forces CppWinRT to generate a complete projection including `base.h`.

**Key insight:** The `-in` flag tells CppWinRT to generate projection headers for those winmds, including `base.h`. The `-ref` flag only makes types available for resolution without generating headers. The distinction matters for triggering `base.h` generation.

### 3. WebView2 Targets Import

**False assumption:** Installing the WebView2 NuGet and referencing its winmd is sufficient.

**Reality:** The WebView2 NuGet package includes a targets file (`build\native\Microsoft.Web.WebView2.targets`) that handles generating C++/WinRT projection headers via its own `wv2winrt` tool. If you do not import this targets file, the WebView2 headers may not be generated.

**Solution:** Import the WebView2 targets in your vcxproj:
```xml
<Import Project="..\packages\Microsoft.Web.WebView2.{version}\build\native\Microsoft.Web.WebView2.targets"
        Condition="Exists('...\Microsoft.Web.WebView2.targets')" />
```

---

### 4. MSIX Package Manifest: EntryPoint Must Be "Windows.FullTrustApplication"

**False assumption:** The `EntryPoint` attribute in the manifest's `<Application>` element should be the executable name (e.g., `MyApp.exe`).

**Reality:** For WinUI 3 **desktop** (Win32) packaged apps, `EntryPoint` must be `Windows.FullTrustApplication`. Setting it to the exe name causes Windows to treat the app as a UWP CoreApplication, which initializes the wrong threading model (ASTA vs. STA).

**Symptom:** `0x8001010E` (RPC_E_WRONG_THREAD) thrown from `twinapi.appcore.dll` inside `Application::Start`. The error originates in `CoreApplicationFactory` -- a UWP code path that should never execute for desktop apps.

**Solution:**
```xml
<Application Id="App"
  Executable="MyApp.exe"
  EntryPoint="Windows.FullTrustApplication">
```

---

### 5. MSIX Package Must Declare Framework Dependencies

**False assumption:** Installing the Windows App Runtime framework package on the system is sufficient; the app will find it automatically.

**Reality:** The MSIX manifest must explicitly declare `<PackageDependency>` elements for the WinAppSDK framework and VCLibs. Without these, the framework packages are not in the app's package graph and WinRT activation fails.

**Symptom:** `0x80040154` (REGDB_E_CLASSNOTREG) -- the class `Microsoft.UI.Xaml.Application` cannot be created because the framework DLLs are not loaded.

**Solution:**
```xml
<Dependencies>
  <TargetDeviceFamily Name="Windows.Desktop" MinVersion="10.0.17763.0" MaxVersionTested="10.0.26100.0" />
  <PackageDependency Name="Microsoft.WindowsAppRuntime.1.6"
    MinVersion="6000.519.329.0"
    Publisher="CN=Microsoft Corporation, O=Microsoft Corporation, L=Redmond, S=Washington, C=US" />
  <PackageDependency Name="Microsoft.VCLibs.140.00.UWPDesktop"
    MinVersion="14.0.33728.0"
    Publisher="CN=Microsoft Corporation, O=Microsoft Corporation, L=Redmond, S=Washington, C=US" />
</Dependencies>
```

### 6. MSIX Package Must Specify ProcessorArchitecture

**False assumption:** Omitting `ProcessorArchitecture` from the `<Identity>` element defaults to the correct architecture.

**Reality:** Omitting it produces a "neutral" package that cannot resolve architecture-specific framework dependencies (the WinAppSDK framework is x64/arm64-specific).

**Symptom:** Same as above (0x80040154) -- framework packages are not resolved because a neutral package cannot depend on architecture-specific frameworks.

**Solution:**
```xml
<Identity Name="..." Publisher="..." Version="..." ProcessorArchitecture="x64" />
```

---

### 7. MSIX Package Needs resources.pri and Compiled XAML (XBF)

**False assumption:** A bare exe with the AppxManifest is enough for a packaged WinUI 3 app to launch.

**Reality:** WinUI 3 requires:
- **Compiled XAML files (.xbf)** -- the binary representation of your XAML pages, generated by the XAML compiler during build.
- **resources.pri** -- a Package Resource Index file that maps resource names (including XAML files) to their physical locations in the package.

Without these, the XAML framework cannot find or load your UI definitions.

**Solution:** Include all `.xbf` files from the build output in the package (maintaining relative paths, e.g., `Themes\Generic.xbf`). Generate `resources.pri` using `makepri.exe`:
```
makepri.exe createconfig /cf priconfig.xml /dq "en-US" /o
makepri.exe new /pr <layout_dir> /cf priconfig.xml /of resources.pri /o
```

### 8. The "x-generate" Resource Language Placeholder

**False assumption:** The manifest from the project template is deployment-ready.

**Reality:** Visual Studio project templates use `<Resource Language="x-generate"/>` as a placeholder that the build system replaces with actual languages. If you package manually without the build system, this placeholder remains and causes deployment failure.

**Symptom:** `0x80070057` -- "the specified resource language 'x-generate' is not a valid language."

**Solution:** Replace with an actual BCP-47 language tag:
```xml
<Resource Language="en-us"/>
```

---

### 9. Package Install Location Is Read-Only

**False assumption:** Files in the MSIX package can be opened for read-write access at runtime.

**Reality:** The package install directory (`C:\Program Files\WindowsApps\...`) is read-only for the app. Any file that needs to be modified at runtime (save files, mutable configuration, disk images) must be copied to a writable location first.

**Symptom:** `CreateFile` with `GENERIC_WRITE` fails with access denied. Memory-mapped files with `PAGE_READWRITE` fail silently (handles remain `INVALID_HANDLE_VALUE`).

**Solution:** On first launch, copy mutable files from the package to the app's local data folder:
```cpp
auto localFolder = winrt::Windows::Storage::ApplicationData::Current().LocalFolder().Path();
// Copy from package install location to localFolder, then open from there
```

---

### 10. InProcessServer Class Registrations

**False assumption:** A packaged WinUI 3 desktop app does not need activatable class registrations in its manifest because it uses C++ direct instantiation.

**Reality:** While the main `winrt::make<App>()` call uses C++ factories directly, the XAML framework may internally attempt WinRT activation for your app's types (e.g., for XAML type info providers, custom controls). Adding `<InProcessServer>` registrations ensures all activation paths work.

**Solution:**
```xml
<Extensions>
  <Extension Category="windows.activatableClass.inProcessServer">
    <InProcessServer>
      <Path>MyApp.exe</Path>
      <ActivatableClass ActivatableClassId="MyApp.App" ThreadingModel="both" />
      <ActivatableClass ActivatableClassId="MyApp.MainWindow" ThreadingModel="both" />
      <ActivatableClass ActivatableClassId="MyApp.XamlMetaDataProvider" ThreadingModel="both" />
    </InProcessServer>
  </Extension>
</Extensions>
```

## Part 2: Recommended Improvements

The following are improvements to the Windows App SDK, MSIX packaging system, and Windows platform that would have significantly reduced the friction encountered during this migration.

### Windows App SDK

1. **Version coupling should be documented prominently.** The relationship between CppWinRT NuGet version, Windows SDK cppwinrt version, and generated header compatibility is not documented anywhere obvious. A compatibility matrix or build-time warning would prevent hours of debugging static assertion failures.

2. **WebView2 dependency should be automatic.** When a project takes a dependency on WinAppSDK 1.6+, the build system should automatically bring in the WebView2 NuGet (or at minimum, produce a clear error explaining the missing dependency). Having the SDK's own headers fail to compile because of a missing transitive dependency is a poor developer experience.

3. **CppWinRT `-in` vs `-ref` semantics need documentation.** The distinction between these flags and their effect on `base.h` generation is critical but poorly documented. Most developers encounter it only through cryptic compilation failures.

4. **The CppWinRT NuGet should match the SDK by default.** When the Windows SDK is updated, the CppWinRT NuGet package version referenced by project templates should be updated to match. Alternatively, the version mismatch check should produce a clear diagnostic message pointing to the solution.

### MSIX Packaging

5. **`makeappx.exe` should validate manifest semantics.** Currently, `makeappx.exe` happily creates packages with invalid resource languages (`x-generate`), missing framework dependencies, and incorrect entry points. A validation pass with actionable error messages would catch these before deployment.

6. **Provide a "package from build output" tool.** The gap between "I have a built exe" and "I have a deployable MSIX" requires deep knowledge of manifest authoring, PRI generation, XBF placement, and framework dependency declarations. A single tool that takes a build output directory and produces a valid MSIX (inferring dependencies from the binary's imports) would be transformative.

7. **Error messages during deployment should be actionable.** Errors like `0x80040154` during app launch give no indication that the cause is a missing `<PackageDependency>` in the manifest. The deployment system knows which class failed to activate -- it should suggest checking framework dependencies.

8. **The relationship between EntryPoint values and app models should be documented at the error site.** Getting `RPC_E_WRONG_THREAD` because `EntryPoint` was set to the exe name instead of `Windows.FullTrustApplication` is nearly impossible to diagnose without deep platform knowledge. The error should say: "Desktop app detected using CoreApplication activation path. Did you mean EntryPoint='Windows.FullTrustApplication'?"

### Windows Platform

9. **Package install location write-access policy should produce clear diagnostics.** When `CreateFile` fails in a package directory, the error is a generic access-denied. A platform diagnostic (Event Log entry, or debugger output message) explaining "Write denied: package install directory is read-only; use ApplicationData.LocalFolder for mutable files" would save significant debugging time.

10. **Framework package resolution failures need better diagnostics.** When a framework dependency cannot be resolved (wrong architecture, version mismatch, etc.), the system should log exactly which dependency failed and why, rather than producing a generic class-not-registered error at activation time.

---

## Summary Checklist for WinAppSDK 1.3 to 1.6 Migration

- [ ] Install `Microsoft.Web.WebView2` NuGet package (no longer bundled)
- [ ] Ensure CppWinRT NuGet version matches your Windows SDK's cppwinrt version, OR avoid adding the SDK cppwinrt path to includes
- [ ] Import WebView2 native targets in your vcxproj
- [ ] Update `packages.config` with new package versions
- [ ] Update all WinAppSDK winmd reference paths (version number in path changes)
- [ ] Verify MSIX manifest has `EntryPoint="Windows.FullTrustApplication"`
- [ ] Verify MSIX manifest has `ProcessorArchitecture` set in `<Identity>`
- [ ] Verify MSIX manifest has `<PackageDependency>` for WindowsAppRuntime and VCLibs
- [ ] Replace `<Resource Language="x-generate"/>` with actual language
- [ ] Include `.xbf` files and `resources.pri` in the package
- [ ] Move any writable data files to `ApplicationData.LocalFolder` at runtime
- [ ] Register app's activatable classes via `<InProcessServer>` in manifest extensions
